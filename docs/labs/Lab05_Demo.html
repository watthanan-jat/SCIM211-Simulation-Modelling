Theory 1: What is a discrete-event simulation?¶

Why we need it¶

Lab 4 simulated one number per day (profit). A queue is different: what happens to one visitor depends on everyone who arrived before. We need to follow the system through time.

A naive approach updates the system every second. But at a help desk almost nothing happens most of the time: the state changes only when someone arrives or someone finishes service. A discrete-event simulation (DES) jumps the clock directly from one event to the next:

$$ 0\longrightarrow T_1\longrightarrow T_2\longrightarrow T_3\longrightarrow\cdots $$

Between events, time passes but the state is constant.

Word Meaning Help-desk example
event an instant at which the state can change a visitor arrives; a service finishes
state what we must know to continue the simulation number in system $N$, next arrival time $t_A$, next departure time $t_D$
counter a running total updated at events number of arrivals so far $N_A$, number of departures so far $N_D$
output measure what we report at the end average wait, longest wait, utilisation, maximum queue length

  5. The scheduled time of the next arrival.

Theory 2: Exponential times — rates versus means¶

The model¶

In an M/M/1 queue, the times between arrivals are independent exponential random variables with rate $\lambda$, and service times are independent exponential random variables with rate $\mu$.

If $T\sim\mathrm{Exponential}(\text{rate }\lambda)$, then

$$ \mathbb P(T>t)=e^{-\lambda t},\qquad \mathbb E[T]=\frac1\lambda . $$

With $\lambda$ per hour, the mean gap is $1/\lambda$ hours, which is $60/\lambda$ minutes.

Why exponential? The memoryless property¶

$$ \mathbb P(T>s+t\mid T>s)=\frac{e^{-\lambda(s+t)}}{e^{-\lambda s}}=e^{-\lambda t}=\mathbb P(T>t). $$

However long a service has already lasted, the remaining time has the same distribution as a fresh one. So to predict the future we only need how many people are at the desk, not how long each has been there. This is why the state of an M/M/1 queue is so small.

What NumPy expects¶

rng.exponential(scale, size) takes the mean (scale), not the rate. This is the same trap as Lab 3 Part B.

Quantity Formula Help desk ($\lambda=5$, $\mu=9$ per hour)
mean gap between arrivals $60/\lambda$ minutes 12 minutes
mean service time $60/\mu$ minutes 6.67 minutes
traffic intensity $\rho=\lambda/\mu$ 0.556

Theory 3: The event-scheduling algorithm (Chapter 7)¶

The state of the single-server queue is

$$ (t,\ N,\ t_A,\ t_D), $$

where $t$ is the clock, $N$ the number in the system (waiting plus in service), $t_A$ the scheduled next arrival and $t_D$ the scheduled next departure. The event list has only these two entries, and the simulation always processes the one with the smaller time.

Pseudocode: M/M/1 event scheduling (Chapter 7)¶

  1. Initialisation. Set $t=0$, $N=0$, $t_A=-\frac1\lambda\ln U_1$, $t_D=\infty$.
  2. Determine next event. If $t_A<t_D$, process an arrival. Otherwise process a departure.
  3. Arrival event.
    • Set $t\leftarrow t_A$.
    • Set $N\leftarrow N+1$.
    • Schedule the next arrival: $t_A\leftarrow t-\frac1\lambda\ln U$.
    • If $N=1$, the server was idle, so schedule a departure: $t_D\leftarrow t-\frac1\mu\ln U'$.
  4. Departure event.
    • Set $t\leftarrow t_D$.
    • Set $N\leftarrow N-1$.
    • If $N>0$, schedule the next service completion: $t_D\leftarrow t-\frac1\mu\ln U$.
    • If $N=0$, set $t_D\leftarrow\infty$.
  5. Record statistics. Update queue length, waiting time, and utilisation statistics.
  6. Repeat until the stopping rule is satisfied.

From pseudocode to Python¶

  • $-\frac1\lambda\ln U$ is an exponential draw with rate $\lambda$ (inverse transform, Chapter 5). In code it is arrival_rng.exponential(mean_gap) with mean_gap = 60 / arrival_rate minutes; similarly service_rng.exponential(mean_service) for $-\frac1\mu\ln U'$.
  • $t_D=\infty$ is np.inf.
  • Step 2 is if t_A < t_D: ... else: .... When the two times are equal, the departure is processed first — the same convention as Lab 5.
  • Every code cell below is labelled with the step number it implements.

Common mistake (Chapter 7). Writing $t_A=-\ln(U)/\lambda$ every time, that is, $t_A=\text{new gap}$, instead of $t_A=t+\text{new gap}$. A gap is a duration; $t_A$ is a clock time.

Demo 2: The event list by hand¶

Step 0 — two random-number streams¶

The pseudocode uses $U$ for arrivals and $U'$ for services. We give them separate generators: one for gaps and one for service times. Then visitor $k$ always receives the $k$-th gap and the $k$-th service time, whatever order the events happen in. Demo 8 shows why this matters.

We will restart these two streams several times, so we write a small helper once.

In [5]:
def make_streams(seed):
    # One generator for gaps (U) and one for service times (U').
    # NEW: SeedSequence(seed).spawn(2) makes two independent child seeds.
    arrival_seq, service_seq = np.random.SeedSequence(seed).spawn(2)
    return np.random.default_rng(arrival_seq), np.random.default_rng(service_seq)

Record every visitor: 12 visitors¶

The algorithm is unchanged: Steps 1–4 are the event-3 cell. We add only the counters from the Chapter 7 table and the recording in Step 5:

  • $N_A$ = number of arrivals so far, $N_D$ = number of departures so far, so $N=N_A-N_D$.
  • One server serves in arrival order, so the arriving visitor is visitor $N_A$, the departing visitor is visitor $N_D$, and the visitor who starts service is always the next one, visitor $N_D+1$.
  • So recording is just append: the $k$-th arrival time, the $k$-th start and the $k$-th departure all belong to visitor $k$.

Stopping rule (Step 6): stop scheduling arrivals after the 12th visitor, and stop the loop when all 12 have left ($N_D=12$).

def simulate_help_desk(arrival_rate, service_rate, n_visitors,
                       arrival_rng, service_rng):
    # Event scheduling for an M/M/1 help desk (Chapter 7). Times in minutes.
    # One row per visitor: arrival, service, start, end, wait, time_in_system.
    mean_gap = 60 / arrival_rate
    mean_service = 60 / service_rate

    # Step 1. Initialisation
    t, N = 0.0, 0
    N_A, N_D = 0, 0
    t_A = arrival_rng.exponential(mean_gap)
    t_D = np.inf
    arrival, service, start, end = [], [], [], []

    # Step 6. Stopping rule
    while N_D < n_visitors:
        # Step 2. Determine next event
        if t_A < t_D:
            # Step 3. Arrival event
            t = t_A
            N = N + 1
            N_A = N_A + 1
            arrival.append(t)                          # Step 5. record
            if N_A < n_visitors:
                t_A = t + arrival_rng.exponential(mean_gap)
            else:
                t_A = np.inf
            if N == 1:
                service_time = service_rng.exponential(mean_service)
                t_D = t + service_time
                start.append(t)                        # Step 5. record
                service.append(service_time)
        else:
            # Step 4. Departure event
            t = t_D
            N = N - 1
            N_D = N_D + 1
            end.append(t)                              # Step 5. record
            if N > 0:
                service_time = service_rng.exponential(mean_service)
                t_D = t + service_time
                start.append(t)                        # Step 5. record
                service.append(service_time)
            else:
                t_D = np.inf

    visits = pd.DataFrame({"visitor": np.arange(1, n_visitors + 1),
                           "arrival": arrival, "service": service,
                           "start": start, "end": end})
    visits["wait"] = visits["start"] - visits["arrival"]
    visits["time_in_system"] = visits["end"] - visits["arrival"]
    return visits

Theory 4: The FCFS shortcut for one server¶

The idea¶

With one server and first-come-first-served, visitors are served in arrival order, and visitor $i$ can start only when

  1. visitor $i$ has arrived, and
  2. visitor $i-1$ has left.

So

$$ \boxed{\;\texttt{start}_i=\max(\texttt{arrival}_i,\ \texttt{end}_{i-1}),\qquad \texttt{end}_i=\texttt{start}_i+\texttt{service}_i\;} $$

with $\texttt{end}_0=0$. Subtracting $\texttt{arrival}_i$ gives the Lindley recursion for waiting times:

$$ \texttt{wait}_i=\max\big(0,\ \texttt{wait}_{i-1}+\texttt{service}_{i-1}-(\texttt{arrival}_i-\texttt{arrival}_{i-1})\big). $$

Why it gives the same event times¶

The event list and the recursion follow the same rules: arrivals join at the back, the desk serves one visitor at a time, and the next visitor starts the moment the previous one leaves. Given the same arrival and service times, they must produce the same start and end times. The recursion simply computes them visitor by visitor instead of event by event.

When the shortcut is not enough¶

The recursion relies on "one server, served in arrival order". With two advisers, priority visitors, visitors who give up and leave, or breaks, the order of service is no longer the order of arrival. Then there is no simple recursion, and we need the event list (with more event types and a record of who is waiting).

Theory 5: Output measures and their conventions¶

Output Definition Notes
waiting time of visitor $i$ $\texttt{start}_i-\texttt{arrival}_i$ time in the line only
time in system $\texttt{end}_i-\texttt{arrival}_i$ waiting plus service
average / longest wait mean / maximum over visitors the longest wait is a single extreme value, so it is very variable
utilisation $\dfrac{\text{total service time}}{\text{last departure}-\text{first arrival}}$ fraction of time the adviser is busy in that window
queue length $Q(t)$ $\max(N(t)-1,\,0)$ waiting visitors only, excluding the one in service
maximum queue length $\max_t Q(t)$ an integer

Every one of these involves a choice (which window, whether the visitor in service counts, which event comes first at a tie). Other choices give other numbers, so the choice must be stated. Theory 6: M/M/1 theory — stability and steady state¶

Traffic intensity and stability¶

$$ \rho=\frac{\lambda}{\mu} =\frac{\text{work arriving per hour}}{\text{work the server can do per hour}} . $$

  • If $\rho<1$, the desk can keep up on average. Queues form by chance and then clear.
  • If $\rho\ge1$, work arrives at least as fast as it can be done. The queue does not settle down; for $\rho>1$ it grows roughly linearly in time.

Steady-state formulas (Chapter 7, valid only for $\rho<1$)¶

$$ \mathbb E[N]=\frac{\rho}{1-\rho},\qquad W=\frac{1}{\mu-\lambda},\qquad W_q=\frac{\rho}{\mu-\lambda}. $$

$W$ is the mean time in system and $W_q$ the mean wait in the queue, in hours; multiply by 60 for minutes.

What "steady state" means¶

If the desk ran for ever, the distribution of $N(t)$ would settle down to a fixed long-run distribution. The formulas describe that long-run regime. They do not describe a desk that opens empty at 9:00, and they say nothing about one particular run. (Chapter 8 explains why the distribution settles, using Markov chains.)

def mm1_theory(arrival_rate, service_rate):
    # Steady-state M/M/1 values (times in minutes); NaN when the queue is unstable.
    if arrival_rate >= service_rate:
        return {"rho": arrival_rate / service_rate, "E[N]": np.nan, "W": np.nan, "W_q": np.nan}
    rho = arrival_rate / service_rate
    return {
        "rho": rho,
        "E[N]": rho / (1 - rho),
        "W": 60 / (service_rate - arrival_rate),
        "W_q": 60 * rho / (service_rate - arrival_rate),
    }

Demo 7b: Which question are we asking? Terminating versus steady state¶

Suppose the help desk is a 2-hour drop-in session: it opens empty, accepts arrivals for 120 minutes, and then serves whoever is still waiting. The empty start is now part of the real system, not an artefact. This is a terminating simulation (Chapter 9); the long-run $W_q$ is a steady-state quantity.

The only change to the function is the stopping rule (Step 6): stop accepting arrivals at the closing time instead of after $n$ visitors, and stop the loop when arrivals have stopped and the desk is empty. The number of visitors is now random. The three changed lines are marked # CHANGED.

In [32]:
def simulate_session(arrival_rate, service_rate, closing_time,
                     arrival_rng, service_rng):
    # Same as simulate_help_desk, but arrivals stop at closing_time (minutes).
    mean_gap = 60 / arrival_rate
    mean_service = 60 / service_rate

    # Step 1. Initialisation
    t, N = 0.0, 0
    N_A, N_D = 0, 0
    t_A = arrival_rng.exponential(mean_gap)
    if t_A > closing_time:             # CHANGED: nobody may arrive at all
        t_A = np.inf
    t_D = np.inf
    arrival, service, start, end = [], [], [], []

    # Step 6. Stopping rule
    while t_A < np.inf or N > 0:       # CHANGED: arrivals over, desk empty
        # Step 2. Determine next event
        if t_A < t_D:
            # Step 3. Arrival event
            t = t_A
            N = N + 1
            N_A = N_A + 1
            arrival.append(t)
            t_A = t + arrival_rng.exponential(mean_gap)
            if t_A > closing_time:     # CHANGED: no arrivals after closing
                t_A = np.inf
            if N == 1:
                service_time = service_rng.exponential(mean_service)
                t_D = t + service_time
                start.append(t)
                service.append(service_time)
        else:
            # Step 4. Departure event
            t = t_D
            N = N - 1
            N_D = N_D + 1
            end.append(t)
            if N > 0:
                service_time = service_rng.exponential(mean_service)
                t_D = t + service_time
                start.append(t)
                service.append(service_time)
            else:
                t_D = np.inf

    visits = pd.DataFrame({"arrival": arrival, "service": service, "start": start, "end": end})
    visits["wait"] = visits["start"] - visits["arrival"]
    return visits

Theory 7: Replications, confidence intervals, and common random numbers¶

One replication = one observation (Chapter 7)¶

Visitors inside one run are dependent: if visitor 10 waited a long time, visitor 11 probably did too. So we cannot treat 400 waits from one run as 400 independent observations. Instead, a whole run is one observation. For replication $r$ let

$$ X_r=\text{average wait in replication } r,\qquad r=1,\dots,R . $$

Different replications use different random numbers, so $X_1,\dots,X_R$ are independent, and the Lab 4 machinery applies unchanged:

$$ \bar X=\frac1R\sum_{r=1}^R X_r,\qquad \bar X\pm1.96\,\frac{s_X}{\sqrt R}. $$

What replications fix, and what they do not¶

Noise (run-to-run variation) Bias (systematic error)
Example five seeds give 49 to 116 minutes every run starts empty and is too short to reach steady state
Reduced by more replications? yes, like $1/\sqrt R$ no
What the CI shows the noise nothing — the CI is centred on the biased value

The interval estimates the mean of what the simulation computes (here: the average wait of 400 visitors from an empty start). Whether that equals the quantity you care about is a modelling question.

Comparing two policies: paired replications¶

To compare policy A with policy B, run both with the same seeds, so replication $r$ of both policies sees the same arrivals and the same service requirements. Then analyse the differences $D_r=X_r^A-X_r^B$:

$$ \mathrm{Var}(\bar D)=\frac{\mathrm{Var}(X^A)+\mathrm{Var}(X^B)-2\,\mathrm{Cov}(X^A,X^B)}{R}. $$

Positive correlation between the paired runs makes the variance of the difference smaller than for independent runs. This is common random numbers, the same idea as the controlled cost check in the Lab 4 demo.

def mean_confidence_interval(values, z=1.96):
    # Approximate CI for the mean: mean +/- z * s / sqrt(n)  (the Lab 4 function).
    values = np.asarray(values)
    mean = values.mean()
    sample_sd = values.std(ddof=1)
    standard_error = sample_sd / np.sqrt(len(values))
    return mean, sample_sd, standard_error, mean - z * standard_error, mean + z * standard_error

Demo 9: A strong interpretation¶

The evidence (help desk, $\lambda=8.5$ per hour, 20 paired replications of 400 visitors):

Service rate 9 Service rate 11
mean of run average waits about 51 min about 16 min
95% CI about [40, 62] about [14, 18]
steady-state $W_q$ 113 min 18.5 min
paired reduction about 35 min, CI about [25, 44], 20 of 20 replications

Under this model, training the adviser to serve 11 instead of 9 visitors per hour would cut the average wait at peak demand from about 51 to about 16 minutes, and the reduction appears in every paired replication. I would recommend it if the training can actually reach that service rate, which should be checked by timing real services after a pilot. The absolute waits come from 400-visitor runs that start empty; for continuous operation at this load the true long-run wait would be higher, while for a short drop-in session it would be lower, so the size of the effect depends on which situation the desk is really in. The model also assumes exponential times, a constant arrival rate, and visitors who never give up.

A strong recommendation connects:

  1. the size of the effect and its confidence interval;
  2. how consistent the effect is across paired replications;
  3. whether the run matches the real question (terminating or steady state);
  4. model limitations;
  5. a practical next action.

Final theory map¶

Rates and means: $\mathbb E[\text{gap}]=60/\lambda$ minutes, $\mathbb E[\text{service}]=60/\mu$ minutes; rng.exponential(scale=mean).

Event scheduling (Chapter 7 pseudocode): 1 initialise $(t,N,t_A,t_D)=(0,0,\text{first gap},\infty)$; 2 next event is the smaller of $t_A$ and $t_D$; 3 arrival: $N\leftarrow N+1$, $t_A\leftarrow t+\text{gap}$, and if $N=1$ schedule a departure; 4 departure: $N\leftarrow N-1$, schedule the next completion if $N>0$, else $t_D=\infty$; 5 record; 6 repeat until the stopping rule.

FCFS shortcut (one server): $$ \texttt{start}_i=\max(\texttt{arrival}_i,\texttt{end}_{i-1}),\qquad \texttt{end}_i=\texttt{start}_i+\texttt{service}_i . $$

Stability and steady state: $\rho=\lambda/\mu<1$; $$ \mathbb E[N]=\frac{\rho}{1-\rho},\qquad W=\frac1{\mu-\lambda},\qquad W_q=\frac{\rho}{\mu-\lambda}. $$

Replications: one run = one observation $X_r$; $\bar X\pm1.96\,s_X/\sqrt R$.

Distinctions to leave with¶

This … … is not this
a gap (duration) an arrival time (clock time)
a rate $\lambda$ per hour a mean $60/\lambda$ minutes
one run's average wait the expected wait
the mean of a 400-visitor run from empty the steady-state $W_q$
noise (shrinks with more replications) bias (does not)
a terminating question (a session, a rush) a steady-state question (long run)
resetting the seed once per policy (controlled comparison) resetting it in every replication (bug)

Common errors¶

  • Passing the hourly rate as NumPy's scale (Demo 1).
  • Setting the next arrival to a gap instead of the current time plus a gap.
  • Using interarrival gaps as arrival times (forgetting the cumulative sum or "$t$ +").
  • Letting service start before arrival, or before the previous visitor has left.
  • Counting the visitor in service as "waiting" without saying so.
  • Calling a finite overloaded run stable because it finishes.
  • Treating the 400 waits inside one run as independent observations.
  • Expecting more replications to remove the gap between a run from empty and $W_q$.
  • Comparing policies with different seeds, or with one shared stream whose draws get out of step.
  • Resetting the generator to the same seed in every replication.
  • Making a decision from one random run.
